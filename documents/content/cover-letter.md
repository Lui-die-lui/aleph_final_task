## 현장의 불편을 서비스로 바꾸는 개발자

플루트를 전공하고 레슨 강사로 활동하며, 레슨 수요가 있어도 시작하기까지가 번거롭고 불투명하다는 것을 자주 느꼈습니다. 가격을 알기 위해 문의부터 해야 했고, 시간을 맞추려면 메시지를 여러 번 주고받아야 했습니다. 구두로만 진행된 상담 때문에 불이익을 겪거나, 강사와 연락하기 어렵고 가격도 불분명해 배우기를 미루는 사람도 곁에서 보았습니다. 해결하고 싶은 문제였지만, 당시에는 그 방법을 알지 못했습니다.

이후 쇼핑몰 웹디자이너로 일하며 상세 페이지 제작과 딜 세팅 등 반복되는 업무를 경험했습니다. 이를 더 효율적으로 바꿀 방법을 고민하면서 화면 뒤의 데이터와 처리 흐름에 관심을 갖게 되었습니다. 웹 개발 과정과 풀스택(ERP 개발) 과정을 병행하며 Java와 Spring Boot로 백엔드의 기본을 익혔습니다. 배운 내용을 제가 잘 아는 문제에 적용하고자 레슨 예약 플랫폼 MUZIN을 기획하고 개발했습니다.

앞으로도 현장의 업무 규칙과 사용자의 불편을 먼저 이해하고, 이를 서비스로 구체화하는 일을 하고 싶습니다. 쇼핑몰 운영과 서비스 개발 경험을 바탕으로 실제 업무의 제약을 살피고, 필요한 기능으로 연결하겠습니다.

## MUZIN : 예약 정책을 코드와 운영 환경으로 연결했습니다

MUZIN은 가격과 가능한 시간을 확인하고 예약할 수 있도록 만든 레슨 예약 플랫폼입니다. 기획부터 프론트엔드, 백엔드, 배포까지 혼자 맡아 mu-zin.com으로 공개했습니다.

가장 오래 고민한 부분은 예약 상태와 정책이었습니다. 요청을 저장하는 것만으로는 충분하지 않았습니다. 요청·확정·취소·완료로 상태가 바뀌는 과정에서 허용되는 행동이 일관되지 않으면, 수강생과 아티스트가 다시 메시지로 상황을 확인해야 하기 때문입니다. 각 상태에서 가능한 변경을 도메인 메서드로 정리하고, 허용되지 않는 변경을 거절하는 테스트를 작성했습니다. 정책이 달라질 때 어떤 로직을 함께 수정해야 하는지도 살피며 업무 규칙과 코드의 관계를 익혔습니다.

초기에는 AI에 크게 의존하지 않고 핵심 구조를 직접 구현했습니다. 시간이 걸렸지만, 이 경험이 이후 AI를 활용할 때 기존 구조와 공통 응답 형식을 기준으로 결과를 검토하는 바탕이 되었습니다. 서비스에 AI 레슨 추천 기능을 넣을 때도 같은 기준을 적용했습니다. 사용량과 월 예산을 제한하고, 가격과 예약 가능 시간은 AI가 생성하지 않고 서버가 DB에서 조회해 응답에 반영하도록 했습니다. 추천 설명과 실제 거래 정보를 분리해, AI가 가격이나 일정을 임의로 안내하지 않도록 구성했습니다.

구현한 서비스를 AWS EC2에 배포하고 GitHub Actions로 자동 배포를 구성했습니다. 배포 후에는 폴링 방식으로 조회하던 알림을 채팅에서 이미 사용하던 WebSocket 연결로 전달하도록 변경했습니다. 기존 연결을 활용해 주기적인 조회 요청을 줄이는 방향으로 개선하며, 기능 구현 이후의 운영 방식까지 고민했습니다.

## 제 코드뿐 아니라, 함께 연결될 구조를 이해합니다

RunnersHigh 팀 프로젝트에서는 다른 팀원의 로직을 충분히 이해하지 못해 문제의 원인을 추적하는 데 시간이 걸렸습니다. 이후 문제·원인·해결 과정을 Notion에 정리해 공유했습니다. 이 경험을 통해 협업에서는 각자의 기능을 완성하는 것만큼 연결되는 코드와 데이터 흐름을 이해하는 일이 중요하다는 것을 배웠습니다.

다음 프로젝트인 OMIJOY에서는 초기 파일과 라우터 구조를 정리하고, Figma 와이어프레임으로 함께 참고할 화면과 기능의 기준을 마련했습니다. 마이페이지를 구현할 때도 다른 팀원이 작성한 코드와 API 응답을 확인해 연결했습니다. 반복 UI의 분리 기준을 개선하고 React Query와 커스텀 훅으로 데이터 처리 로직을 분리하며, 공통 구조와 재사용을 고려했습니다.

최근 외부 LLM 게이트웨이 팀 프로젝트에서는 담당 작업을 마친 뒤 전체 흐름을 QA하다가, 차단된 요청을 관리자가 일시적으로 허용하는 임시 권한 기능이 동작하지 않는 것을 발견했습니다. AI를 활용해 관련 코드를 확인한 결과 처리 API가 누락되어 있었습니다. 확인한 근거를 팀원들과 공유하고 논의한 뒤 해당 API를 직접 구현했습니다. 이 경험을 통해 담당 영역 밖에서 발견한 문제도 원인과 영향을 확인하고, 팀과 수정 범위를 합의한 뒤 해결하는 태도를 갖게 되었습니다.

## 고객의 화면과 운영자의 판단을 함께 생각합니다

쇼핑몰 웹디자이너로 일하며 상세 페이지와 배너, 오픈마켓 딜 페이지를 제작했습니다. 같은 상품도 어떤 정보를 먼저 보여주고 어떤 순서로 설명하느냐에 따라 고객이 이해하기 쉬운 정도가 달라진다는 것을 체감했습니다. 이 경험은 개발을 시작한 뒤에도 정보를 보는 사람과 목적에 따라 화면을 구성하는 바탕이 되었습니다.

개발 프로젝트에서는 고객에게 보이는 화면과 함께 운영자가 확인해야 할 정보도 다뤘습니다. Odyssey Plan에서는 가입자와 AI 요청 통계를 확인하는 대시보드를, MUZIN에서는 방문 기록을 집계하는 기능을 만들었습니다. 사용자에게 필요한 기능을 제공하는 것에서 나아가, 운영자가 서비스 이용 현황을 파악할 수 있는 정보도 함께 고민했습니다.

입사 후에는 각 담당자의 업무와 판단 기준을 이해하고, 팀의 업무 방식과 협업 기준을 익히겠습니다. 이를 바탕으로 고객과 운영자의 요구사항을 구체화하고, 실제 업무에 도움이 되는 화면과 기능으로 구현하겠습니다.
